# Architecture and decision log

Blockwright is an independent website for Minecraft creators. It is a small
platform (shell + tool registry) whose first tool is the **Character Builder**.
Not an official Minecraft service; not approved by or associated with Mojang or Microsoft.

## Key decisions

| # | Decision | Why |
|---|---|---|
| D1 | Player skins target **Java Edition** first: a 64×64 RGBA PNG in the standard atlas, classic (4 px) or slim (3 px) arms. | A skin PNG can only recolour the fixed player body. Bedrock skin import differs by platform, so it is documented, not promised. |
| D2 | Custom 3D characters target **Bedrock Edition** as a `.mcaddon` (behavior pack + resource pack, each a `.mcpack`). | That is the documented way to add a new entity type. A Bedrock add-on is not a Java mod or a player skin. |
| D3 | Manual and photo-assisted paths are deterministic and work with **no GPU and no AI**. AI providers are optional adapters behind runtime capability checks. | PLAN §0.3 — honest, useful, valid exports even when models are unavailable. |
| D4 | The 3D entity preview renders **the exporter's own output** (`.geo.json` + atlas) through a Blockbench-convention parser, not the editor state. | The preview cannot drift from what is exported (PLAN §6.3). |
| D5 | Exact pixel data never round-trips through `<canvas>`. Skins and atlases are plain RGBA buffers encoded/decoded with `fast-png`. | Canvases premultiply alpha and change RGB of translucent pixels, which would break lossless PNG round trips. |
| D6 | Web pins `three@0.156.1`, shared by `skinview3d` (which requires `^0.156.0`, i.e. 0.156.x only) and `@react-three/fiber` 9 (`>=0.156`). `@react-three/drei` 10 needs `>=0.159`, so it is **not used**; Three's own `OrbitControls`, `GridHelper` and `AxesHelper` are used instead. | One Three.js copy in the bundle, no "multiple instances" issues. |
| D7 | TypeScript is pinned to 6.0.x (not 7.x). | `typescript-eslint` 8.72 supports `<6.1.0`. |
| D8 | Python worker uses CPython 3.12 (installed with `uv`); model runtimes live in separate virtual environments. | Matches Sking's published environment; keeps heavy ML deps out of the CPU worker. |
| D9 | Node API owns uploads, projects, jobs and exports; the Python worker owns AI inference and mesh→cuboid geometry. | PLAN §2.2. Slow inference never runs inside a browser request. |
| D10 | Storage is the local filesystem (`DATA_DIR`) with per-record JSON manifests, atomic writes, TTL expiry; an object-store adapter can replace it later. | PLAN §6.4, no database needed for v1. |
| D11 | Photo-assisted sampling runs in the browser using the shared TS packages (pure functions, unit tested). | Interactive guide boxes; works even if the worker is down. Results are re-validated by the API on save/export. |
| D12 | Anonymous sessions: the API issues HMAC-signed random session tokens (header `X-Session-Token`). Every asset/project/job/artifact stores the owner's session hash; non-owners get 404. | No accounts in v1, but user A cannot fetch user B's files by guessing IDs. |

## Repository layout

```text
apps/web            Vite + React + TS site and tools (features/<tool-id>)
apps/api            Express 5 + TS REST API (/api/v1)
services/ai-worker  Python 3.12 FastAPI worker (AI adapters, mesh -> cuboids)
packages/shared     zod schemas/contracts, error codes, RGBA raster + PNG helpers
packages/minecraft-skin   skin atlas, validation, symmetry, legacy conversion, templates, photo projection
packages/bedrock-export   atlas packer, .geo.json writer/reader, pack builder, add-on validator, templates
scripts/            export verification, fixtures, worker launcher
fixtures/           original test skins/entities/photos (all generated by this repo)
docs/               this documentation
```

Workspace packages are ESM, built with `tsc -b` to `dist/`. Tests and the Vite dev
server resolve them to their TypeScript sources (`vitest.aliases.ts`), so a stale
build is never what gets tested.

## Coordinate and UV conventions (entity)

Defined once in `packages/bedrock-export/src/faces.ts` and proven by tests.

- **Bedrock frame** (what `.geo.json` contains): model pixels (1/16 block), Y up,
  cube `origin` = minimum corner, pivots absolute. Entities face **north (−Z)**;
  the entity's right side is at **negative X** (as in vanilla humanoid geometry).
- **Blockbench frame** (what the preview draws): X mirrored — `from.x = −(origin.x + size.x)`,
  `pivot.x = −pivot.x`, rotation `[−rx, −ry, rz]`, Euler order `ZYX`. Transcribed
  from Blockbench's Bedrock codec (`parseCube`/`parseBone`) and `CubeFace.UVToLocal`.
- **Face bitmaps** are stored as seen from outside the cube, upright. `up` has the
  front (north) edge at the top; `down` has the back (south) edge at the top.
- **JSON UVs** follow Blockbench's exporter: side faces `uv=[x,y]`, `uv_size=[w,h]`;
  `up`/`down` faces `uv=[x+w,y+h]`, `uv_size=[−w,−h]`. Omitted faces are not drawn.
- Geometry format `1.12.0` (per-face UV is part of it; Blockbench only bumps to
  `1.21.0` for `uv_rotation`, which we never write).

Tests (`geometry.test.ts`) check for every face that the bitmap appears unmirrored
from outside (cross product of its top/left edges points inward) and that the
natural top-left texel lands on the top-left corner; and that export → import
preserves every cube and every face texel.

## Skin atlas

`packages/minecraft-skin/src/layout.ts`: the standard box-UV net per part
(head 0,0 / hat 32,0; torso 16,16 / jacket 16,32; right arm 40,16 / 40,32;
left arm 32,48 / 48,48; right leg 0,16 / 0,32; left leg 16,48 / 0,48).
Verified in tests against the UVs that `skinview3d`'s own `SkinObject` assigns to
every box face (classic and slim), and the legacy 64×32 conversion is checked
against the copy table published in `skinview-utils` (`convertSkinTo1_8`).

## Texture atlas strategy (entity)

`packages/bedrock-export/src/atlas.ts`. Exact mode first (one texel per model unit,
one rectangle per face, shelf-packed into the smallest power-of-two size up to
512 px). If that does not fit, solid faces share 4×4 colour swatches (UV on the
inner 2×2, so nearest-filter sampling never bleeds); bitmap faces stay exact. Above
`LIMITS.maxAtlasSize` (1024) the export fails with `MODEL_TOO_COMPLEX`.

## Add-on structure

```text
<ns>_<name>.mcaddon (ZIP)
├── <ns>_<name>_BP.mcpack (ZIP)
│   ├── manifest.json            format_version 2, module "data", depends on RP header uuid+version
│   ├── pack_icon.png            front-view render of the model
│   └── entities/<ns>.<name>.json            minecraft:entity (1.12.0), summonable + spawn egg
└── <ns>_<name>_RP.mcpack (ZIP)
    ├── manifest.json            format_version 2, module "resources"
    ├── pack_icon.png
    ├── entity/<ns>.<name>.entity.json       minecraft:client_entity (1.10.0)
    ├── models/entity/<ns>.<name>.geo.json   minecraft:geometry (1.12.0)
    ├── textures/entity/<ns>/<name>.png
    ├── render_controllers/<ns>.<name>.render_controllers.json  (1.8.0)
    └── texts/en_US.lang, texts/languages.json
```

File names and the texture folder include the namespace so two add-ons with the
same entity name never override each other's resources by path. UUIDs are fresh
per export. `min_engine_version` is `[1, 21, 0]`.
